# T1-D — Leaderboards and competitive records

Baseline `ba47e0f`. The Toy player can open an all-time or weekly board by Volume and voluntarily submit from an eligible live result. The board allocation is ELSEWHERE 1, DAYBREAK 2, DESCENT 3 and ORBIT 4. Slot 5 is reserved.

## Platform contract

- One official SDK loader serves Toy-hosted App and PC Web. The container path remains App-gated. Rank calls probe their own `isSupport` capabilities. Standalone static preview stays offline and keeps the game playable. The inspected public SDK rejects writes on `/toy/preview`.
- `getRankList({ board, period, limit })` returns ordered `{ rank, score, nickname, avatar }` rows and supports guest reads. `getMyRank({ board, period })` requires sign-in and returns `{ ranked, rank, score }`. `submitScore({ board, score })` takes an absolute integer from −16,777,216 to 16,777,215 and returns `{ score }` with the caller's all-time high-water score. The SDK documents both `all` and `week`, and breaks ties by earliest achievement. The public API accepts boards 1–5. The publisher's interactive reference and the shipped validator agree on 1–5. The embedded declaration has older 1–3 comments. Weekly rollover timing and live propagation from a submission remain platform checks. [Publisher SDK reference](https://www.bilibili.com/toy/publish/sdk) · [Public SDK client](https://s1.hdslb.com/bfs/seed/toy/app/sdk/toy-sdk.js)
- The platform handles first-submission data consent. Public rows supply display names and optional CDN avatars. The implementation omits the separate profile call. Login and permission errors have dedicated copy. `http_error` / `307044` activates a shared cooldown with bounded exponential backoff and jitter. The service quota is shared across the Toy. Reads are cached for two minutes per board, period and session epoch, and concurrent identical reads are coalesced. Refresh and retry are opt-in. There is no polling or fixed QPS assumption. [Official request guidance](https://github.com/bilibili/toy/blob/main/skills/toy/references/content-checklist.md#7-用了云存储--排行榜调用节奏上线后才爆的那类)

## Settlement and request lifetime

- At the existing results transition, Runtime emits one immutable settlement for the active run. It binds a transient run ID, frozen policy and actual seed to the real result, original local score and recovery counts. The record store continues to commit by its existing rules. Runtime has no platform or network dependency.
- The Toy eligibility check requires an interactive Standard Normal escape, ordinary random seed policy, and zero neutralized gates in main and Encore. T1-D began with Main route eligibility. T1-E-F2 expanded it to all three recorded routes. Manual and Auto Boost, pauses, muted play and recovery without neutralized gates retain eligibility. The total uses the same integer main score plus earned Encore bonus as local records. Invalid values are rejected at the boundary. The production result action receives only the live settlement. [Current eligibility and score ceilings](../toy-development.md#leaderboards-and-competitive-records)
- Submission is single-flight per run and a successful attempt consumes the current result. A six-second UI deadline keeps Results usable. While the SDK still owns an unresolved write, retry stays locked to avoid concurrent submission for that run. The platform's high-water semantics cover explicit retries after a completed failure. Successful writes invalidate the affected board's cache entries for both periods. Results requests the affected all-time list once to show the board leader alongside the current total and local best. Opening the board reuses that list and separately reads personal rank. SDK permission prompts can outlast the UI deadline.
- Showing a cached board avoids a network request. Closing or changing panels detaches the displayed query. The account-change indicator, visibility return and container close invalidate stale tasks and private state. Where supported, the browser's cookie change event signals a Bilibili account change by cookie name. The game does not read or retain its value. SDK clients provide no documented account-change event, so the UI also clears the cache epoch on foreground return. Silent in-place account changes without a browser event remain a hosted check.
- The browser produces these scores. These checks enforce the product eligibility rules for this client. They provide no server-authoritative verification of a modified client. [Bilibili developer FAQ](https://www.bilibili.com/opus/1241171666570051585)
