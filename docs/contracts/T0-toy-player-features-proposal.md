# T0 Toy player features proposal

Status as of 2026-11-28 · Proposed. Ship the four-volume, local-first game before enabling platform services. The [audit](../audits/T0-toy-platform-compatibility.md) distinguishes the public SDK client interface from behavior that requires authorized documentation and a hosted test.

## Container integration

Use one Toy-side adapter for loading the official SDK, capability checks, host event subscriptions and calls. The game can open its menu and start without an SDK response. Keep settings language and orientation independent of host state. Show a fullscreen or immersion action only if the current host or browser can perform it.

- In a supported Bilibili App container, use the shipped `isSupport(...)` and state query/subscription before enabling an opt-in orientation and immersion action. Use `setContainerMode({ orientation, immersive })` with the saved orientation for an explicit player action. Inputs accept `portrait`, `landscape` and `auto`, and the requested fields may be provided independently. The FAQ places orientation and immersion at App 9.9.0 or newer. Treat returned and observed container measurements as authoritative for layout. Avoid a forced startup transition or a new blocking rotation prompt. [Official FAQ `III.7](https://www.bilibili.com/opus/1241171666570051585) · [Public SDK](https://s1.hdslb.com/bfs/seed/toy/app/sdk/toy-sdk.js)
- Apply safe-area and capsule measurements to UI padding using host coordinates after verifying their units and origin. Fall back to CSS `env(safe-area-inset-*)` and measured viewport size. Combine insets only after agreeing on the coordinate space so the same inset is counted once. Resize the canvas and input surface through the current resize path after the container settles. Actual rotation uses the existing pause and resume policy. Resizes from browser chrome alone leave the run intact.
- Use generation checks for pending native mode changes and ignore stale callbacks after disposal. Unsubscribe on teardown. Feed an available `onPageClose(listener)` signal into the existing lifecycle after confirming its ordering. Verify real suspend, return, native close and WebGL restore in app. A native Exit action requires a user gesture and an available `closeBrowser()`. Preserve host Back and the Web fallback.
- In desktop Bilibili Web and unsupported containers, use existing standards-based behavior if permissions and a trusted gesture allow it. Fullscreen, orientation lock and pointer lock can fail inside a hosted container. Test App and Web separately, and omit controls that cannot work. Preserve both orientations, touch steering and the existing optional Immersive Mouse. Screen orientation preference stays useful as a setting even when native locking is unavailable. ## Leaderboards

### Board allocation and SDK boundaries

Use board 1 for ELSEWHERE, 2 for DAYBREAK, 3 for DESCENT and 4 for ORBIT. Reserve 5. Public platform material advertises weekly boards and first arrival winning ties. The downloaded SDK validates an integer score from −16,777,216 through 16,777,215 and integer board IDs 1–5. It exposes `submitScore({ board, score })`, `getRankList({ board, period, limit })` and `getMyRank({ board, period })`. The read period mapping includes `all` and `week`. Present Lifetime and Weekly only after confirming that eligible submissions populate both windows and verifying the reset boundary, tie ordering, supported list limits, rank/profile response fields, permissions and current client support. The official checklist describes per-player submissions as idempotent high-water updates. ### Competitive eligibility

All four volumes offer Normal and Impossible. Current scores depend on difficulty multiplier, boost, combo, clean crossings, resonance, route modifiers, gate counts and Encore. The records store keys Standard Best by volume/course revision and difficulty. Completed and terminated runs can update a local Best under today's rules when recovery has not neutralized any gate. Sightseeing has a separate Last. Showcase is Standard Impossible internally, with scoring and persistence disabled. [Run policy](../../app/game/core/run-policy.ts) · [Simulation scoring](../../app/game/core/simulation.ts) · [Encore scoring](../../app/game/core/encore.ts) · [Route multipliers](../../app/game/core/branches.ts) · [Records](../../app/game/runtime/records.client.ts)

| Candidate format | Competitive implications |
| --- | --- |
| Fixed Normal, Main route, escaped only | Initial T1-D format. Same nominal chart and route within a volume. Existing randomized openings and pickups still introduce run variance. |
| Fixed Normal, all routes, escaped only | Adopted in T1-E-F2. Preserves route choice as a competitive strategy. Higher modifiers, alternate gate counts and branch risk can favor a route. |
| Fixed Impossible, Main route, escaped only | Clear expert challenge under the 3.4× multiplier, one life and Impossible chart. Fewer qualifying players and more sensitivity to legal route and seed variation. A possible future special board. |
| Fixed competitive seed | Reduces opening/pickup variance and rewards practice. Creates a new approved player contract that must be exposed explicitly. Defer in the first release. |

The current rules accept a newly finished, real interactive Standard Normal run with a recorded Main, Challenge or Bonus route, `ESCAPED`, zero neutralized main and Encore gates, normal product seed policy and no diagnostics or forced options. Standard still supports free choice of route, difficulty and ordinary growth of the local Best and Last. Submit the same nonnegative floored main score plus earned Encore bonus used by `totalRunScore`. Confirm the score ceiling in focused tests before enabling submission. Reject out-of-range data without clamping or re-scaling ranks. Explain eligibility in the menu or Results. Show the cause of ineligibility where useful. Keep pause, legitimate silent fallback and ordinary recovery that did not neutralize a crossing governed by the production rules. [Current eligibility and score ceilings](../toy-development.md#leaderboards-and-competitive-records)

Derive an immutable candidate when the genuine run settles, using its frozen policy and final result, before UI replay or any local retry. Keep a run identity and at most one submission in flight. A Toy result adapter supplies fields to the platform and handles status. Never submit a stored legacy Best, an imported/cloud result, a Showcase or Sightseeing run, or a result preview. A future rule revision needs a new compatible board epoch or an explicitly coordinated reset. The platform FAQ says removing a user clears their entries across boards, so this is a moderation constraint.

Only fetch a board or player rank when requested or when a relevant surface opens. Cache reads in memory by board, period and player session. Use a single in-flight request per key and an explicit refresh. Post a qualifying result once for opted-in/authorized players. On a retryable failure, keep an in-session candidate and offer a bounded backoff with jitter. The checklist identifies rate-limit response `http_error` / `307044` and advises against hardcoded QPS assumptions. Distinguish sign-in, missing permission, unsupported client, empty board and temporary failure. Never block gameplay or Results. Guard late responses by session and board generation.

The score originates in a browser. SDK validation and product rules help with consistency. A modified client can forge a submission. Confirm platform moderation options before launch, and describe the standings as community leaderboards. ## Optional cloud save

Keep local V1 records authoritative for play. Propose `sofaraway_toy_v1` as a private per-player cloud key. Store the course revision, personal Bests grouped by volume and difficulty, an optional recent result and an allowlist of portable preferences in a validated versioned envelope. Exclude raw input, per-frame state, SDK identifiers and contact or profile data. Keep quality, orientation and mouse capture device-local. Sync language only on explicit opt-in, and retain manual local language changes. `getCloudStorage(keys)` reads a key list, `setCloudStorage(items)` writes a batch and `removeCloudStorage(keys)` removes keys. Confirm value/total size, quotas, serialization and permission behavior in the authorized docs. [SDK bundle](https://s1.hdslb.com/bfs/seed/toy/app/sdk/toy-sdk.js) · [Cloud save FAQ ``III.11, 12, 21](https://www.bilibili.com/opus/1241171666570051585)

Merge validated matching Bests by maximum. Discard unknown schemas, mismatched course revisions and malformed values. Keep local Last as the device's last successfully committed run. If recent results are added, first prefer showing device and cloud recent entries separately. Derive a global Last only if the platform exposes trustworthy ordering metadata or a suitable transactional primitive. Client clocks do not establish global order. Batch on settlement, explicit sync and sparse preference checkpoints. Use a read-merge-write with coalescing, account/generation checks and bounded retry. Concurrent remote writes can still race without compare-and-set. Preserve local Best, reconcile on later reads and decide whether stronger coordination is needed before enabling cloud by default. A failed or unavailable sync leaves the game playable.

Store local settings, V1-shaped records, handoff IndexedDB and Web Lock names under a stable Toy namespace if sibling Toy paths share an origin. Use a separate installation/account scope for pending sync metadata and discard that metadata on account change. Do not automatically upload anonymous local data to a new Bilibili account. Cross-Toy shared storage is unnecessary for this product. Keep the cloud service optional and within the Toy build.

## Result sharing

Add a single optional Results action. Start with a native Toy link and a concise local card showing Volume, mode, difficulty, outcome, route and production score where applicable. Render the card from structured result data. Avoid user-entered text, photo upload and external targets. Use a clean Toy entry link, with an optional read-only packaged result path or hash that cannot affect gameplay, set seeds or submit scores. The public SDK exposes `share({ path, … })`, `getQrCode({ path, size })` and App-side `sharePicture({ base64Data })` and `saveImageToAlbum(...)`. Probe supported image inputs, permissions and result path validation before enabling image sharing. Browser Web can use in-container QR or the visible local card where the SDK supports it. Keep nicknames and avatars optional, fetched only when the player chooses a feature that needs them and rendered as safe text/image data. Use text-only attribution to SoFarAway, LibreCosta and HelloRun. No engagement-based unlocks are needed. ## Recommended sequence

1. Build the isolated local player package and bilingual Settings. Keep the game fully usable with a missing or denied SDK and get physical-device evidence for the core game before enabling App-only mode or native assumptions.
2. With creator permission and explicit approval to upload a preview, verify the SDK signatures, return payloads and supported versions in the authorized docs and hosted environment. Test current iOS, Android at and above 9.9.0, a supported older client for fallbacks, and desktop Bilibili Web. Exercise container lifecycle and safe areas, audio activation, ORBIT/WebGL, storage and navigation.
3. Enable optional leaderboards with the agreed eligibility contract and observe fair-score distribution. Add cloud save and result-image sharing after quotas, permissions and conflict behavior have been measured. Release each as an independently optional Toy-side capability.
