## Runtime boundaries

- **Application** owns route state, preferences and accessible UI. `GameViewport` loads the runtime after hydration and consumes read-only snapshots through `useSyncExternalStore`. React issues commands through [`GameRuntime`](../app/game/contracts.ts) and stays outside the fixed-step and drawing loops.
- **Runtime** owns the canvas session, renderer, RAF, input listeners, run lifecycle and audio transport. Retries and volume switches reuse the runtime. Async work must respect the current generation. Context restoration rebuilds GPU resources while retaining the run, including the random layout. BFCache suspends the runtime, and permanent teardown disposes it.
- **Simulation** owns deterministic charts, movement, crossings, lives, scoring and results. It runs without a browser. [`Path`](../app/game/graphics/path.ts) and [`BranchPath`](../app/game/graphics/branch-path.ts) are shared Three.js vector math that can be imported by Node. WebGL, DOM input and audio stay in their client modules.
- **Graphics** owns the visual scene and reads simulation state. Volume-owned materials, textures and reusable templates outlive streamed chunks. Chunks dispose their own geometry. Debug previews use the runtime generators with their own resource owners. ELSEWHERE-specific art belongs in its own paths and presets.
- **Audio** owns Web Audio activation, the per-run output bus, scheduling and synthesis. Runtime aligns its anchor to the same run timeline as simulation. Audio callbacks have no authority over scoring or crossings.

The player dictionaries format UI copy, numbers and structured game messages.
Web prerenders the player route in its distribution default and applies the saved locale after hydration.
Locale changes update the React UI and document language while the same runtime owns the run.
The Web home route supplies the CN compliance footer independently of the selected language. [Player dictionaries](../app/i18n/player-text.ts)

The Explorer's [preview surface](../app/game/debug/preview-surface.client.ts) owns one `Graphics` instance, the canvas context listeners and its resize observer. Scenic scenes, endings, the Interface backdrop and ORBIT flights use it to roll back failed setup and dispose on exit. Each preview retains its scene and redraw state. ORBIT retains its own restoration, flight frames, input and audio transport.

The Web adapter, Toy player and Explorer drive the engine through their own entry points. The engine reads production game data and stays independent of React Router, Explorer pages and test harnesses. [Web diagnostics](verification.md#web-diagnostics) enter through the Web adapter. The [Toy player](../toy/ToyPlayer.tsx) supplies volume state and scoped player preferences to the same viewport. Its build erases the runtime's diagnostic branches and checks rendered modules for forbidden imports. [Toy development](toy-development.md)

## Time, space and recovery

[`clock.ts`](../app/game/core/clock.ts) defines a monotonic run timeline and 60 Hz simulation. User pauses, background suspension and graphics interruptions freeze the timeline. Ordinary stalls leave bounded catch-up debt. Audio skips expired scheduling steps and resumes on its original grid. A later audio interruption can fall back to silent play and offer a gesture to restore sound at the current offset.

[`reference-track.ts`](../app/game/core/reference-track.ts) converts authored beats into fixed main-path stations. Simulation advances by arc length, interpolates the player's local position at each crossing and judges each event once. Boost changes arrival time. Musical time still drives sections, light and the song end. On branches, the same station maps to route-specific arc length, including the length difference carried through the merge. The [world-space contract](contracts/D0-B2-F2-world-space-gameplay-graceful-recovery.md) records the model and why it replaced beat-locked crossings.

DAYBREAK, DESCENT and ORBIT use a 1.15× longitudinal reference in Impossible Standard. Cruise meets the authored cues while Boost retains the same proportional lead as the base difficulties. The gates, centerline, junctions and world bounds use that reference. Side routes still take their measured travel time. ELSEWHERE uses its original station layout and the separate Impossible Encore.

Standard has three base difficulties and Impossible, with a faster speed ramp and added gates between Hard anchors. See [DAYBREAK Impossible validation](audits/D1-B2-validation.md) for its chart and ending contract and the [DESCENT facility contract](contracts/D2-A0-descent-facility.md) for its CONTROL accents. Sightseeing uses five lives, one-third forward speed, a sparser chart and the same song duration. The fixed pickup, branch layout and obstacle shapes have separate sources in [`pickups.ts`](../app/game/core/pickups.ts), [`branches.ts`](../app/game/core/branches.ts) and [`collision.ts`](../app/game/core/collision.ts). Branch and pickup randomness use independent streams. Rendering and collision must agree on the opening and spatial station of each gate. Technical recovery can neutralize an unobservable crossing without rewarding or penalizing the player. See [`simulation.ts`](../app/game/core/simulation.ts) for the results semantics.

Showcase runs Standard Impossible at cruise speed with scoring disabled. The [pilot](../app/game/core/showcase-pilot.ts) plans through the real openings on the selected seeded branch, supplies ordinary steering each fixed tick, and remains subject to collision even while catching up. The shared music transport determines the run duration, and Encore gates beyond cruise range stay unreached. The runtime keeps the flight HUD and all record writes disabled. For reproducible browser captures, `?mode=showcase&route=bonus&seed=1` selects the route and seed.

The [record store](../app/game/runtime/records.client.ts) saves completed run intents under one origin-scoped exclusive Web Lock. It reads and writes the original V1 localStorage document while holding the lock. One IndexedDB row hands the last successful document to the next lock holder because a different renderer can still read a stale localStorage cache. The handoff is consulted only during commits. Last follows successful commit order, and failed intents can be retried on the next completion in the same runtime. When either coordination API is unavailable, the remaining localStorage path is best effort. Coordination covers clients using the same lock protocol.
